# Политика безопасности

Мы относимся к безопасности проекта **nina_tennis** серьёзно. Этот документ описывает, как сообщать об уязвимостях и какие версии поддерживаются.

## Сообщение об уязвимости

Если вы обнаружили уязвимость безопасности, **пожалуйста, не создавайте публичный Issue**.

### Куда отправлять приватные отчёты

- **Через GitHub:** используйте функцию [Privately reporting a security vulnerability](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability) в репозитории (вкладка Security → Report a vulnerability).
- **Или приватно владельцу репозитория** через контакт в профиле GitHub.

### Что указать в отчёте

- Описание уязвимости и её потенциального влияния
- Шаги для воспроизведения (POC, если возможно)
- Версия бэкенда/фронтенда, операционная система, версия Node.js
- Предлагаемое исправление (если есть)

### Правила публикации

- **Не публикуйте** детали уязвимости публично (Issue, блог, соцсети) до выпуска исправления.
- Мы подтверждаем получение отчёта в течение **48 часов**.
- Сроки выпуска исправления зависят от серьёзности (см. ниже).
- После исправления мы публично опубликуем Security Advisory с благодарностью исследователю (по желанию).

## Известные меры безопасности в проекте

- **JWT-авторизация** с ролевой моделью (`admin` / `referee` / `user`)
- **RolesGuard** на всех записывающих эндпоинтах бэкенда
- **JWT-секрет:** в продакшене обязателен `JWT_SECRET` — без него бэкенд падает с ошибкой. В dev используется небезопасная заглушка **только для локальной разработки**.
- **Хеширование паролей** через bcryptjs (salt rounds 10)
- Судьи могут редактировать **только матчи своего турнира** (проверка scope на бэкенде)

## Поддерживаемые версии

Мы поддерживаем только последнюю версию на ветке `main`.

| Версия | Поддержка | Обновления безопасности |
|--------|-----------|------------------------|
| `main` (последний релиз) | ✅ Да | ✅ Выпускаются |
| Старые коммиты | ❌ Нет | ❌ Нет |

Обновляйтесь до последней версии ветки `main`, чтобы получать исправления безопасности.

## Сроки выпуска исправлений

| Серьёзность (CVSS) | Целевой срок |
|--------------------|--------------|
| Критическая (9.0–10.0) | 1–3 дня |
| Высокая (7.0–8.9) | 3–7 дней |
| Средняя (4.0–6.9) | 1–2 недели |
| Низкая (< 4.0) | Следующий релиз |

## Ответственное раскрытие

Мы ценим ответственное раскрытие уязвимостей. Исследователи, первыми сообщившие о валидной уязвимости, будут упомянуты в Security Advisory (с их согласия).
