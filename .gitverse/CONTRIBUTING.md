# Руководство для контрибьюторов

Спасибо за интерес к проекту **nina_tennis**! Этот документ описывает, как предлагать изменения, оформлять pull request'ы и какой стиль кода мы ожидаем.

## Как предложить изменения

### Через Issues

Перед тем как писать код, создайте [Issue](../../issues) с описанием:

- **Баг:** что произошло, шаги для воспроизведения, ожидаемое и фактическое поведение, скриншоты/логи
- **Фича:** какую проблему решает, предлагаемый подход, альтернативы

Используйте шаблон (если есть) или опишите проблему максимально подробно.

### Через Pull Request

1. **Сделайте fork** репозитория и создайте ветку от `main`:
   ```bash
   git checkout -b feat/краткое-описание
   ```
2. Внесите изменения. Назовите ветку осмысленно: `feat/...`, `fix/...`, `docs/...`, `refactor/...`.
3. **Убедитесь, что код собирается и тесты проходят** (см. ниже).
4. Создайте Pull Request в `main` с заполненным описанием.

## Правила оформления Pull Request

### Структура описания PR

```
## Что сделано
Краткое описание изменений.

## Почему
Какую проблему это решает / какую фичу добавляет.

## Как протестировано
Что проверено вручную или автотестами.

## Скриншоты (если UI)
До/после для визуальных изменений.
```

### Чек-лист перед отправкой PR

- [ ] Ветка создана от `main` и называется по схеме `тип/описание`
- [ ] Код проходит typecheck: `tsc --noEmit` без ошибок в изменённых файлах
- [ ] Бэкенд собирается: `cd apps/backend && npm run build`
- [ ] Существующие тесты не сломаны
- [ ] Если добавлена логика — есть unit-тесты (`libs/shared`)
- [ ] Нет закомментированного кода и `console.log` в продакшен-коде
- [ ] COMMIT-сообщения осмысленные (на русском или английском)

## Требования к коду

### Стиль

| Слой | Правила |
|------|---------|
| **TypeScript** | Строгая типизация, без `any` в новых эндпоинтах (только legacy). Имена — в `camelCase`, типы/интерфейсы — `PascalCase`. |
| **React/Next** | Функциональные компоненты, хуки. Server Components по умолчанию, `"use client"` только где нужен interactivity. |
| **NestJS** | Контроллеры тонкие, логика в сервисах. Гварды через `@UseGuards`, роли через `@Roles`. DTO с `class-validator`. |
| **CSS** | TailwindCSS. Использовать дизайн-токены (`bg-surface-card`, `text-content`), поддержка тёмной темы (`dark:`). |

### Коммиты

Формат сообщений: `тип: описание` на русском.

```
feat: добавлена страница участника
fix: исправлено налезание карточек сетки
docs: обновлён README
refactor: вынесена логика скоринга в shared
test: добавлены тесты посева
chore: обновлены зависимости
```

### Тесты

- **Логика скоринга/посева** → unit-тесты в `libs/shared/src/*.spec.ts` (Jest)
- **E2E авторизации** → `apps/backend/test/*.e2e-spec.ts` (Jest + supertest, нужна MongoDB)
- Покрывайте новую бизнес-логику тестами, не только UI

## Процесс ревью

1. **Автопроверки:** после открытия PR убедитесь, что typecheck и сборка проходят.
2. **Ревью:** мейнтейнер проверит архитектуру, стиль, безопасность, тесты. Ожидайте комментарии — это нормально.
3. **SLA:** первые комментарии — в течение 3–5 рабочих дней. Для срочных PR отметьте владельца в комментарии.
4. **Слияние:** послеapproval PR вливается в `main`. История — через merge-коммиты (не squash), чтобы сохранить контекст.
